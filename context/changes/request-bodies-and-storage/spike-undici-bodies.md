# Spike: what undici writes for a request with a body

## Assumption
Plan A1. Negative result: different bytes, a `content-length` that cannot be recorded, a moved `Content-Type`,
or a method that refuses a body.

## Prediction (written before running)
"Sends all, connection changes": "All seven send the bytes with content-length, except that GET, DELETE, OPTIONS
and HEAD write connection: close because they don't expect a payload." (author's choice, 2026-11-06)

## What happened
A scratch script sent requests through undici to a raw `net` server, which recorded header lines and bytes without
Node's HTTP parser. The body was `{"a":"zażółć"}`, 18 bytes in UTF-8.

```
GET     host, connection: keep-alive, X-A, content-type, content-length: 18   bytes 18
HEAD    host, connection: close,      X-A, content-type, content-length: 18   bytes 18
DELETE  host, connection: keep-alive, X-A, content-type, content-length: 18   bytes 18
OPTIONS host, connection: keep-alive, X-A, content-type, content-length: 18   bytes 18
POST    host, connection: keep-alive, X-A, content-type, content-length: 18   bytes 18
PUT     host, connection: keep-alive, X-A, content-type, content-length: 18   bytes 18
PATCH   host, connection: keep-alive, X-A, content-type, content-length: 18   bytes 18
```

Other cases:
- `content-length` listed last with the right value: the same bytes on the wire, for all seven.
- `Content-Type` listed before `X-A`: position and case kept (`GET`, `DELETE`, `POST`).
- Empty `Uint8Array`: identical to no body. `content-length: 0` on `POST`, `PUT`, `PATCH`; none on the others.
- 2 MiB on `POST` and on `GET`: all bytes, `content-length: 2097152`.
- Listed `content-length: 3` with 18 bytes: `POST` throws `UND_ERR_REQ_CONTENT_LENGTH_MISMATCH` with nothing written; `GET` writes
  `content-length: 18` with no error.

## Verdict: holds
The bytes and headers are predictable for all seven methods, including `HEAD`.

## Surprises
- **The prediction was wrong.** `connection` does not change on `GET`, `DELETE` or `OPTIONS`. It stays `keep-alive`. `HEAD` is `close`, as it is
  without a body. The `expectsPayload` branch at `client-h1.js:1215` did not change what `connection` says.
- **A mismatched `content-length` behaves differently by method.** `POST` refuses and `GET` silently corrects. Only `wire.ts` computing the value keeps
  the record true. `UND_ERR_REQ_CONTENT_LENGTH_MISMATCH` is classified as `network` today.
- **`HEAD` sends a body.** Nothing refuses it.
- **Not settled:** the number of new connections per request was irregular. No field in a record depends on it, so it was not pursued.
- **Not tried:** `content-length` listed anywhere but last. `wire.ts` always lists it last.

## What this means for the plan
- Phase 1's wire contract: `content-length: <bytes>` last when there is a body, generated by `wire.ts`. `Content-Type` goes where `wire.ts` lists it.
  `connection` follows the rule that exists today.
- An empty text box records `body: null`. Bytes of length zero are not a separate case on the wire.
- `UND_ERR_REQ_CONTENT_LENGTH_MISMATCH` belongs with `invalid-request`.
- Whether the form offers a body on `HEAD` turns on curl, not undici (`spike-curl-bodies.md`).
